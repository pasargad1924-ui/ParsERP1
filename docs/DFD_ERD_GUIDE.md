# راهنمای یادگیری: سطوح DFD و مفاهیم ERD

## بخش اول — سطوح دیاگرام جریان داده (DFD)

DFD را معمولاً در چند **سطح جزئیات** می‌کشند. هر سطح همان سیستم است، فقط نزدیک‌تر زوم می‌کند.

### سطح Context (سطح ۰)
- کل نرم‌افزار **یک فرایند** است.
- فقط نشان می‌دهد سیستم با **بیرون** چه داده‌ای رد و بدل می‌کند.
- مثال پارس‌ئی‌آرپی:
  - ورودی از: کاربر، تأمین‌کننده، مشتری، فایل اکسل
  - خروجی به: گزارش، فاکتور، گواهی، موجودی

هدف: مرز سیستم مشخص شود؛ داخل هنوز باز نشده.

### سطح ۱
- همان جعبهٔ سطح ۰ را باز می‌کنیم به **چند فرایند اصلی** (خرید، انبار، تولید، سریال، فروش، گارانتی، حسابداری).
- مخازن دادهٔ مهم (جداول کلی) دیده می‌شوند.
- فلش‌ها بین ماژول‌ها جریان دارند.

هدف: معماری ماژول‌ها و وابستگی داده بین بخش‌ها.

### سطح ۲ (و پایین‌تر)
- **یک** فرایند سطح ۱ را باز می‌کنیم.
- مثال: فقط «انبار» → رسید، حواله، انتقال، تعدیل، گزارش موجودی.
- جزئیات فیلدها هنوز در DFD نیست؛ فقط جریان داده است.

هدف: طراحی دقیق یک ماژول قبل از کدنویسی.

### قواعد مهم DFD
1. هر فلش باید **داده** داشته باشد (نه فقط «کنترل»).
2. فرایند بدون ورودی یا بدون خروجی ناقص است.
3. مخزن داده را مستقیماً به مخزن دیگر وصل نمی‌کنند؛ همیشه از یک فرایند رد می‌شود.
4. نام فرایند بهتر است فعل داشته باشد: «ثبت رسید»، «صدور حواله».

### DFD چه چیزی نیست؟
- ترتیب دقیق زمان‌بندی مثل flowchart نیست.
- ساختار جداول و کلیدها را نشان نمی‌دهد (آن کار ERD است).

## بخش دوم — ERD چیست؟

**ERD (Entity Relationship Diagram)** دیاگرام **موجودیت–رابطه** است.

تمرکز ERD:
- **چه چیزهایی** را ذخیره می‌کنیم (موجودیت / جدول)
- **چه ویژگی‌هایی** دارند (صفات / ستون‌ها)
- **چگونه به هم وصل‌اند** (رابطه + کلید)

### مفاهیم اصلی ERD

| مفهوم | معنی ساده | مثال در پارس‌ئی‌آرپی |
|--------|-----------|---------------------|
| **Entity (موجودیت)** | یک «چیز» قابل ذخیره | کالا، انبار، سریال، مشتری |
| **Attribute (صفت)** | ویژگی آن چیز | نام کالا، کد، تعداد |
| **Primary Key (کلید اصلی)** | شناسه یکتای هر ردیف | ProductId, SerialNo |
| **Foreign Key (کلید خارجی)** | ارجاع به ردیف جدول دیگر | ProductId داخل SerialNumbers |
| **Relationship (رابطه)** | ارتباط دو موجودیت | هر سریال به یک کالا تعلق دارد |

### انواع رابطه از نظر تعداد

1. **یک به چند (1:N)** — رایج‌ترین  
   یک کالا ← چند سریال  
   یک انبار ← چند ردیف موجودی  

2. **چند به چند (N:M)** — معمولاً با جدول واسط  
   سفارش خرید ↔ کالا از طریق PurchaseOrderLines  

3. **یک به یک (1:1)** — کمتر  
   مثلاً یک پروفایل اضافه برای هر کاربر  

### Cardinality (کاردینالیتی)
روی خط رابطه می‌نویسند حداقل/حداکثر:
- `1` الزامی یک
- `0..1` اختیاری
- `1..*` حداقل یکی تا چندتا
- `0..*` صفر تا چندتا

مثال: هر SerialNumbers **حتماً** یک Product دارد (`N:1`).  
یک Product می‌تواند **صفر یا چند** سریال داشته باشد.

### کلید و یکتایی
- **PK:** تکرار نمی‌شود (SerialId).
- **Unique:** مثلاً SerialNo یکتا است حتی اگر PK چیز دیگری باشد.
- **FK:** مقدارش باید در جدول مرجع وجود داشته باشد (یکپارچگی ارجاعی).

### ERD در مقابل DFD

| | DFD | ERD |
|--|-----|-----|
| سؤال اصلی | داده چطور **جریان** دارد؟ | داده چطور **ساختار** یافته؟ |
| عنصر اصلی | فرایند + فلش + مخزن | موجودیت + رابطه + صفت |
| زمان استفاده | فهم فرایند کسب‌وکار | طراحی دیتابیس |
| خروجی عملی | مرز ماژول‌ها | جداول SQL |

هر دو لازم‌اند: DFD می‌گوید «چه کاری»، ERD می‌گوید «چه جدولی».

## ERD خلاصهٔ هستهٔ انبار و سریال

```
[Warehouses] 1 ─── * [Stock] * ─── 1 [Products]
                              │
[StockTransactions] * ────────┘
        │
        └── اختیاری به Serial / سند مرجع

[Products] 1 ─── * [SerialNumbers]
[Users] 1 ─── * [StockTransactions] (CreatedBy)
[Users] 1 ─── * [SerialNumbers] (CreatedBy)
```

جریان کسب‌وکار (DFD) روی این ساختار (ERD) پیاده می‌شود.
